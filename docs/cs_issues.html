  • 安定版の観測の条件は、開発版より緩い（15°・20°、枚数の条件なし）。緩いので、嘘の値を信じて寄せる危険は、寄せが止まっている安定版では実害になっていない。

  • 差分の詳しい一覧は #74。

1. つまみ（走行体に置くテキスト。再ビルド不要）

走行体はリポジトリの checkout なので、ソースの既定値を書き換えても git pull で戻る。そこで ./sorot_spike/<名前>.txt の1行目に 1 か 0 を置いて上書きする。ファイルが無ければソースの既定で動く。 置いたらコミットして残すこと（管理外だったときは作り直しで消え、経路が 40cm 伸びた）。

つまみソースの既定何のためのつまみか
turn_drift.txt1（置いてあるのは 0）旋回中に車体が並進するぶんを、手前の直進の SCD から先に差し引く補正
follow_plan.txt1走りながら自己位置を見て、先の行の SCD/SCR を書き直すか（開ループをやめる）
heading_hold.txt1直進を、ジャイロの向きを保つ直進（FUNCNO 19）で走るか、エンコーダ補正の直進（FUNCNO 5）で走るか
heading_camera.txt1旋回直後の直進に、床のコードで向きを測る SCRIPT を差し込むか
heading_fix.txt0測った向きを、走らせ方の目標だけでなく自己位置にも打ち直すか
position_fix.txt0床のコードから出した位置のずれで自己位置を打ち直すか
gate_check.txt1ゲートをカメラで見て「通れる／当たる」を記録するか（走りは変えない）
gate_steer.txt0ゲートの観測を走りへ返し、中心へ寄せるか
cycle_overrun_ms.txt50周期が何 ms を超えたら記録するか（0 で止める）

各つまみの要点

つまみ要点注意
turn_drift「旋回で後ろへ下がる」ぶんを先に余分に走る理屈。下がらない今の機体では、足したぶんがそのまま行き過ぎになる9/25 に 0 にした。1 のとき直進1本ごとに 2〜3cm、18本で 40cm 超。戻すのは TURN_DRIFT_MM を測り直したときだけ。効いているかは grep "旋回中の並進" ev3_python.log（「相殺: しない」が正しい）
follow_plan9/21 の実機で終点の開きが 84/90/108mm → 23/63mm0 にしても止まりはしない。安定版は 0
heading_holdFUNCNO 5 は滑りで向きがずれても気づかないジャイロは直進するだけで ±5°/80cm の実在しない回転を積む（#54）。保とうとして実際に曲がり、記録では真っ直ぐに見える。それを外から直すのが heading_camera
heading_camera床のコードは動かないので、旋回直後にカメラが格子に対する向きを測って目標を直す直すのは目標だけ。自己位置は heading_fix
heading_fix向きは「操舵の目標」と「x/y を積む方位」の2か所にある。0 だと走りは直っても自己位置が古い向きのまま積み続ける床のコードの一辺のログは 1 のときだけ出る。符号が逆の疑いがある（#76）
position_fix床のコードに当てて x/y を打ち直す自己位置が半マス以上ずれていると隣のコードに当てる（違う場所へ飛ぶ）。実機では未確認
gate_check自己位置の記録は実際の曲がりを隠す。ゲートは動かない外の基準止めも曲げもしない
gate_steer向きを少し振って中心へ寄せる。振ったまま着くと 1° あたり 3.8mm 狭くなるので、遠くで振って 350mm 以内で正面に戻す直せるのは約 49mm まで（片側の余裕 47.5mm）。俯角が狂うとゲートを測れない。安定版は 0（寄せない）
cycle_overrun_msasp は 0.5〜1.25 秒固まることがあり、その間モータは最後の指令のまま走るしきい値を超えたら、どのタスクのどの区間かを1行残す

2. 実測・公式の値（変えない）

カメラが見た画素を床の mm に戻す物差し。1つ違うと距離も間隔も倍率でずれ、原因も見分けがつかない。実測がある量から固定し、残った1つ（俯角）だけを動かす。

量値何のための値か出どころ
色が始まる高さ45.0mm柱の色は床から 45mm 上で始まる。床と思うと間隔が 1.28倍に膨らむ実測
床 → レンズ205.0mm床までの距離はこの高さに比例する実測
足元のすき間230.0mm走行体が通る幅。車体 135mm なので片側の余裕は 47.5mm実測
継手の外径24mmすき間と芯々の差メーカー公式
柱の芯々254.0mmカメラの物差し（検算用）。通れる幅ではない230＋24
車体の前から車軸80.0mm距離の基準点（回っても動かない点）実測
車輪の半径27.5mm回転を距離に直す係数。自己位置のすべてがここに乗る実測
トレッド112.0mm旋回角度の換算実測

柱の芯々は 258 → 248 → 258 → 254 と4回動いた。数字を焼き込まない。

3. 機体ごとのカメラ校正（RoughSpot/Python/2026/camera_calib/<機体>/）

安定版にはこの校正が無く、俯角は 21.0° 固定。 開発版には有る。fx/cy はチェスボードから出る固い値で、俯角だけは写真に写らないので人が入れる。

機体俯角fxcy
scsk218.2°1317.5320.3
scsk322.0°1271.9365.5
読めないとき21.0°1258.8359.5
  • 俯角は定数ではない。柱に当たるたびに動く（1日で約 1°）。信用できるのは 400〜900mm の帯だけ（#60）。
  • 校正が読めたかは起動ログで確かめる。ファイルに 18.2 と書いてあっても、読めなければ 21.0 で走る。

4. ゲートの観測を信じる条件（Python）

カメラは斜めから見たり枚数が足りなかったりすると、平気で嘘の値を出す。嘘の値で寄せると当たる側へ寄せるので、「測れたが信じない」を作ってある。締めすぎると、当たっていた観測まで捨てる。

定数開発版安定版意味
TRUST_APPROACH_DEG10.0°15.0°これより斜めなら観測を信じない
MIN_VERDICT_FRAMES3無し判定に要る枚数。足りなければ「信用できません」と書く
MAX_APPROACH_DEG8.0°20.0°これより斜めなら寄せない
SQUARE_UP_APPROACH_DEG25.0°―近くでは緩める
SQUARE_UP_MM350.0mm―正面へ戻す段に入る距離
MAX_SPAN_ERROR_MM50.0mm―間隔が 254±50 を外れたら測りを疑う

9/25 に一度 5° へ締めたが、当たっていた観測（7.1°・4枚）を捨てて外れた観測（4.4°・2枚）を残したので 10° に戻した。効いていたのは角度より枚数。

5. 打ち直しの上限（Python）

間違えると違う場所へ飛ぶので上限がある。超えたら打ち直さず見送る。

定数開発版安定版意味
MAX_CORRECTION_DEG15.0°5.0°向きの打ち直しの上限（入口 29/2。#59・#62）
MIN_MARKERS4―目印がこれ未満なら位置を出さない
MAX_OFFSET_MM約 82mm―格子の 1/3。超えたら取り違えとみなす
MAX_DEVIATION_DEG6.0°―同上（向き）
TURN_DRIFT_MM-25.9 / 4.6 / -29.7 / 1.1同じ旋回中の並進の見込み。いまの機体には 16〜20mm 大きい

6. C++ の校正定数（走行体で make が要る。版による差なし）

走りそのものを作っている値。速度と電池で変わる値が混ざっているので、速度を変えたら校正が無効になる。

定数値何のためか
STOP_LEAD_TIME0.073s止まる指令から止まるまでの空走を見込んで先に止める。速度に比例し、冷間と温間で 11% 違う
NXT_WHEEL_RADIUS27.5mm回転 → 距離
NXT_WHEEL_INTERVAL112.0mm左右差 → 旋回角度
NXT_WHEEL_TURN_SLIP1.031旋回の横滑り。各輪 PWM 40 で 1.031、100 で 1.333。旋回を速くすると無効
KP_REFERENCE_FWD40ライントレースの P を速度で割り戻す基準
HEADING_CORRECT_MAX_DEG / COORD_CORRECT_MAX_DEG10.0°向きの補正・自己位置の打ち直しの C++ 側の上限（#62）

7. 罠

  • 同じ名前で符号が逆の定数がある。 heading_reader.CAMERA_TO_AXLE_FORWARD_MM = -20、gate_finder は +20。どちらを import したかで 40mm ずれるが、一定のずれなので気づきにくい。
  • 経路の Comment の距離と SCD は別の量。 Comment は PC が書いた補正前、SCD は turn_drift で相殺した後。食い違っていても不具合ではない。
  • 電池を替えたら測り直す量がある（STOP_LEAD_TIME・TURN_DRIFT_MM）。

4ETラリーの入口：向きを揃えてから走り出す

#59
入口（29/2）で止まる向きを、運んだボトルの色によらず揃える

赤を運んだ回だけ入口の向きが +4〜+8° ずれ、10回中8回は打ち直しの上限（5°）を超えて見送っている。赤の運び終わりだけ「白を見るまで右旋回」の古いやり方が残っているため。ボトルの色はランダムなので、本番でも起きる。

対応：赤の 21/11〜21/12 を黄・青と同じ角度だけの旋回にする（または 21/12 の SCR を詰める）。各色3走行で 29/2 の値を見る。

安定版custom_Left/Right.json作り直し不要#54 の本命
#60
カメラの俯角を測り直し、走行ごとに確かめる

会場と本社で俯角が約3°違っていた（設定は 21.0° 固定）。2〜3° ずれると、黒線から測る向きの符号が逆になる回があり、ゲートの距離・横位置も十数%狂う。柱に当たると動く。

対応：本番の機体の俯角を測り直す。走行ごとに、柱の間隔（芯々 254mm）が合っているかを集計で見る。

安定版校正ファイル作り直し不要
#76
床のコード（floor_code）で測った向きの符号が逆の疑いを、確かめる

開発版で起きた件だが、安定版の custom_Left.json も 29/2 で同じ測り方（heading_fix.py）を使っている。符号が逆なら、入口の打ち直しが毎回ずれを増やす。

対応：確かめるだけ。同じ画像を floor_code と目印（markers）にかけ、符号が揃うかを見る。逆なら 29/2 の打ち直しを止める。

分析の本体。対応は #59・#60・#61・#62 に切り出してある。#59 を入れて各色3走行が揃えば閉じる。

安定版まとめ役
#62
向きのずれが 10° を超えると「測り間違い」として捨てられ、本当にずれていても直せない

本当に 10° 回っていたのに、測り間違いとして捨てていた回がある。上限は C++ に2か所あり、片方だけ広げると「当てた」と出て何も起きない。#59 で入口のずれが減れば、10° を超える回そのものが減る。

対応：#59 の結果を見てから決める。先に #76 の符号の確認が要る。

5ETラリーのゲート：経路と当たり判定

#65

安定版判断PC・つまみ

今の経路は6本とも旋回の直後にゲートを通り、手前の直線が 125〜364mm しかない。これでは柱を見て寄せる時間が無い。助走 617mm で直せる横ずれは約 35mm。60秒の上限つきで、取れないゲートは今までどおり。

ゲート通過の着地点に足した 25mm は、後の同じ軸の直進で打ち消す作り。最後の1回だけ打ち消す直進が無く、x が約 +26mm ずれたまま終わる。

KP は旋回の行では「押し直しの許容[度]」。9/22 以降の走行はすべて KP 2。手引きの「押し直すと悪くなる」は 9/14 の布での結果。どちらが正しいか、同じ条件で比べて決める。

クローズ済版に依らない判断PC の値
#66

クローズ済開発版規約の確認#23 と一緒に閉じる
